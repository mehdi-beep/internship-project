**Bugs found and fixed during verification:**
- **Notifications were silently never persisted.** `notification_repository.create()` called `db.flush()` instead of `db.commit()`. Since the Planning row's own `create()`/`update()` already committed its own transaction beforehand, the notification insert was flushed into a transaction that got discarded when the request-scoped session closed — the API call succeeded, no error was ever raised, but the notification never actually reached the database. Caught by the backend E2E test asserting a technician actually received "New Planning Assignment" after being assigned. Fixed by committing in `create()`.
- **Calendar rendered empty in the live app** (looked fine in isolated backend tests) — traced to the frontend requesting `page_size=200` for the month-wide calendar fetch while the `/planning` router capped `page_size` at 100, causing a silent 422 that React Query swallowed without surfacing an error to the UI. Raised the cap to 500 (Planning is an inherently bounded operational dataset — 220 seeded rows total — not a Ch.115 raw-dump concern). This class of bug (silent failed fetch → blank page, no visible error) is worth remembering for future list views with wide date-range fetches.
- **`@fullcalendar/react` was pinned to `^7.0.2` in `package.json` while `core`/`daygrid`/`timegrid`/`interaction` were pinned to `^6.1.21`** (a Phase 1 scaffolding mistake) — caused real TypeScript type-identity errors (duplicate incompatible `EventImpl` types) since v7 is a separate major line from the v6 core it was paired with. Repinned to `^6.1.21` to match.
- **MUI "uncontrolled to controlled input" warning on the New Planning form** — `technician_id` and `priority` used plain `register()` on MUI `<TextField select>` instead of `Controller`, so the select rendered with an `undefined` value on first paint before React Hook Form's binding attached. Fixed by switching both to `Controller`, matching the pattern already used for `client_id`/`site_id`.

**Known minor item (not fixed, low priority):** the "unselected" sentinel value for numeric dropdowns (`client_id: 0`, `site_id: 0`, `technician_id: 0`) triggers a benign MUI dev-console warning ("out-of-range value") since `0` isn't a real ID. **Bugs found and fixed during verification:**
- **State machine/service mismatch (would have 409'd on the very first real approval).** Phase 7's `ALLOWED_TRANSITIONS` table listed `PENDING_TECHNICAL_APPROVAL → TECHNICAL_APPROVED` as the legal move, but `approval_service.decide_technical_approval` (written this phase, consistent with the Phase 6 atomic-transition decision) tries to jump straight to `PENDING_ADMINISTRATIVE_APPROVAL`. The table simply hadn't been updated to match that earlier decision. Caught immediately by the E2E test's very first approval call failing with a 409. Fixed the table, not the service, since the service matches the actual product decision.
- **Audit trail lost the Submitted-vs-Resubmitted distinction after a rejection.** `submit_intervention` (Phase 6/7) decided which audit action to log by checking `intervention.status == REJECTED` — but `update_intervention` already resets a corrected Rejected intervention's status to `Draft` *before* the next submit call ever runs, so that check could never actually be true and every resubmission was silently mislabeled as a first-time `submitted` rather than `resubmitted`. This was a real, if subtle, bug: Ch.18 explicitly lists "Resubmitted" as a distinct audit event, and it was unreachable. Fixed by checking the audit log's own history (`has_ever_been_rejected`) instead of the transient current status, since the log is the one place that fact is still recorded after the status resets. Caught by the reject→edit→resubmit E2E assertion, not by inspection — a good reminder that "the status says X now" and "did X ever happen" are different questions and conflating them is an easy trap.

Both fixes were re-verified against the full Phase 5-8 regression suite (0 failures) before moving on.
